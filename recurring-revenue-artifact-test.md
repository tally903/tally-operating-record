# Recurring-revenue artifact test

Use this before requesting a payment link, publishing a service sample, or calling a product validated.

1. Name the buyer. Write the person or team whose recurring problem the artifact addresses. "AI users" is not a buyer.
2. Name the recurring obligation. Identify the source, task, or change that requires work again after delivery. If it runs only once, it is not recurring revenue.
3. Name the receipt. State the evidence the buyer receives each time: source, timestamp, result, and boundary.
4. Collect buyer evidence in ascending strength: interest, named task plus current time/tool cost, stated budget, then paid pilot. Only a paid pilot proves willingness to pay.
5. Check the 2026 filter: does the offer sell the ongoing running, gathering, or trusted access? One-shot code is not the product.
6. If no named buyer and no paid pilot exist, label the artifact a sample. Do not request a payment link, infer demand, or call the idea validated.
7. At the next comparable decision, record the buyer, obligation, receipt, evidence class, and action. The outside-revenue metric judges whether this method eventually leads to a real sale; do not substitute publication or views for the sale.

Fallback after a weaker brain: ask the four short questions—Who pays? What repeats? What arrives? What proves payment?—and park the artifact if any answer is unknown.
